# 计划核验模块说明（plan-verifier）

> 本模块是**规则核验器**，不是多智能体编排系统。它只回答一个问题：这份计划在“输入内部一致性”和“证据标记”上有没有硬伤。
> 本次新增文件仅三个：`src/lib/agents/plan-verifier.ts`、`tests/plan-verifier.test.mjs`、`docs/核验模块说明.md`。未修改共同类型 `src/lib/agents/plan-contract.ts`、模型客户端、聊天 API、页面、依赖与锁文件。

## 1. 导出与签名

```ts
export function verifyPlan(request: PlanRequest, plan: PlanCandidate): PlanVerification;
```

纯函数：不调用模型、不请求网络、不读取密钥、不生成随机数据、不读取当前时间、不修改传入对象（测试里用 `Object.freeze` 深冻结输入验证过）。

## 2. 输入怎么分

- `request` 由**调用方**保留：校区、用户可用时段、原始任务（含开放时段）、资料证据、`simulation` 标记。计划的生成方不能借 `plan` 改动这些约束。
- `plan` 只有模型生成的步骤；步骤用 `taskId` 指向原始任务。
- 时间一律是同一天内的 `HH:mm`，按分钟比较，不处理跨午夜。
- `campus` 与 `availableWindow` 允许缺失 —— 缺了就返回 `needs_info`，而不是猜。

## 3. 检查项与等级

| 检查 | code | severity | 判定口径 |
| --- | --- | --- | --- |
| 缺校区 / 可用时段 / 任务 / 步骤 / 步骤起止时间 | `missing_input` | needs_info | 每条缺失单独给出“要补什么”，不合并成一句“信息不全” |
| 非法 `HH:mm`，或结束不晚于开始 | `invalid_time` | error | 该区间从后续时间比较中剔除，不再连坐报重叠 |
| 任务未覆盖 / 同任务多步骤 / 未知 taskId / 原始任务 id 重复 | `task_coverage` | error | 第一版约定“每个原始任务恰好一个步骤” |
| 步骤超出用户可用时段 | `outside_available_window` | error | 只核对步骤之间、不核对用户约束是最常见的漏检 |
| 任意两步骤时间重叠 | `time_overlap` | error | `end` 等于下一步 `start` 不算重叠 |
| 步骤校区与选定校区不一致 | `campus_mismatch` | error | 本版本不做跨校区计划 |
| 步骤 id 重复 / 依赖不存在 / 依赖成环 / 依赖未在本步骤前结束 | `dependency_conflict` | error | 环检测用颜色标记 DFS，自带环与长链都不会死循环 |
| 步骤超出任务开放时段 | `outside_service_window` | error | 开放时段本身非法时改报 `invalid_time` |
| 没有依据 / 引用不存在的 evidence id / 证据 id 重复 | `missing_evidence` | needs_info | 无依据的步骤不给“通过”，只给“待补” |
| 未核实的 official、project 依据；真实计划用了 simulation 依据 | `unverified_evidence` | needs_info | `request.simulation=true` 时 simulation 依据合法 |
| 任务缺开放时段 | `unknown_service_window` | warning | 不编造开放时间 |

**状态优先级**：有 `error` → `revise`；否则有 `needs_info` → `needs_info`；否则 `passed`。`warning` 可以与 `passed` 同时返回，但 `passed` 只表示“没查出内部矛盾”，不表示现实事实已核实。

## 4. 实现里的几个口径决定

1. **缺失与非法分开**：缺时间报 `missing_input`（要补），填了但填错报 `invalid_time`（要改）。两者混在一起，调用方就不知道该追问用户还是该退回模型。
2. **非法区间不连坐**：一个步骤时间非法时，只报 `invalid_time`，不参与重叠与开放时段比较，避免同一个错因刷出四五条问题把人淹没。
3. **结构缺失即止**：`tasks` 或 `steps` 为空时只返回 `missing_input`——没有基准，后面的规则全部无意义。
4. **环必须报成 error**：依赖成环的计划永远无法开始，属于必须退回修正，不能降级为提示。
5. **证据分两类**：`missing`（没有或引用不到）与 `unverified`（有但没核实 / 真实计划用模拟依据）。前者是“补材料”，后者是“补核实”，修正动作不同。
6. **输出稳定**：问题按固定规则顺序追加、`stepIds` 去重，同样的输入永远得到同样的输出，便于测试与前端渲染。

### 未执行的部分（如实说明）

任务书给的标准命令是 `node --experimental-strip-types --test tests/plan-verifier.test.mjs`。它在**本机沙箱环境**下失败，原因是测试运行器默认要为每个测试文件起子进程，而沙箱禁止子进程管道通信：

```
Error: spawn EPERM  (errno: -4048, code: 'EPERM', syscall: 'spawn')
```

因此改用上面两条等价命令执行（一条直接跑测试文件，一条关掉进程隔离跑 `--test`），断言与报告格式一致。在你们自己的机器上，任务书里的原命令应当可以直接跑；若同样报 `spawn EPERM`，加 `--test-isolation=none` 即可。

**未执行类型检查**：本机 `node_modules` 正在重建，`pnpm ts-check` 未能运行，TypeScript 严格模式的类型核对需要在你们终端执行一次（本文件按 strict 心智编写，未使用 `any`、枚举与构造函数参数属性）。

另外会看到一条无害告警：

```

```

原因是仓库 `package.json` 没有 `"type": "module"`。本轮不允许改依赖与配置文件，所以保留告警；它不影响测试结果。

## 6. 局限

- **不判断事实真伪**：只读 `verified` 标记，不去核网页、不判断来源是否真实存在。真实资料核对由后续环节负责。
- **不推算通勤**：只做时间区间比较，不计算两校区之间要走多久，也不判断“30 分钟够不够办完一件事”。
- **不处理跨午夜**：`HH:mm` 同一天内比较；`00:00–00:30` 这种零长度以上的非法区间按“结束不晚于开始”一律报错。
- **不做跨校区计划**：本版本一旦发现校区不一致直接判 `revise`，跨校区需要上层先拆段。
- **一任务一步骤**：拆分更细的“一个任务多个动作”会被判 `task_coverage`，这是第一版的刻意约定，改约定要同步改测试。
- **不评价语言表述**：计划文案是否通顺、是否贴合用户语气，不在核验范围内。

## 7. 合入后怎么用

1. 协调员产出计划后先调用 `verifyPlan(request, plan)`；
2. `status === 'revise'`：把 `issues` 原样回传模型，要求按 `suggestion` 修正后重新生成；
3. `status === 'needs_info'`：把 `missing_*` / `unverified_*` 转成对用户的追问或待补材料清单；
4. 通过后连同 `issues`（可能只剩 warning）一起落库，作为“核验与修正记录”；
5. 本模块只提供规则检查，多智能体的任务分配与模型执行仍由主工程负责。
