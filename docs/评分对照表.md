# 赛题要求 → 代码 → 命令 → 证据 对照表

> 用途：评审拿到仓库后，**30 秒内**能确认每条硬要求都落在哪个文件、怎么跑、证据在哪。
> 每一行的命令都在干净环境里跑过；证据路径就是仓库里的文件，可逐行核对。

## 一、五个核心模块（赛题"技术要求 · 平台功能完整性"）

| 要求 | 代码位置 | 怎么看 | 证据 |
| --- | --- | --- | --- |
| Agent 定义与配置 | `configs/agents.json`、`harness/executor.py` | 打开配置：四个角色的提示、工具白名单、记忆开关、模型、版本 | 控制台 S-01；`evidence/T-07.md` 的 `dispatch.log` 里 agent 名 |
| 工作流编排 | `configs/workflow.json`、`harness/orchestrator.py` | N1–N9 九个节点，含 `branch`（条件分支）与 `loop`（回环）两种控制结构 | `python -m harness run --case T-04` 走清洗分支；`--case T-07` 走回环 |
| 任务调度与执行 | `harness/scheduler.py`、`harness/executor.py` | `score = 0.4·match + 0.3·(1−load) + 0.2·norm(priority) + 0.1·succ` | `evidence/T-02.md` 的 `dispatch.log`：`rebind executor-1→executor-2 score=0.81 reason=high_load` |
| 结果验证与监控 | `harness/verifier.py`、`harness/tools.py` | L1 结构 → L2 可执行 → L3 基准真值比对 → L4 交叉复算 → L5 人工放行 | `evidence/T-07.md` 的 `verify_r1.json`（L2 拦下依赖缺失）与 `verify_r2.json`（全绿） |
| 反馈循环与优化 | `harness/loop.py`、`harness/orchestrator.py` 的 `_repair` | 失败类型 → 修正策略映射；三种终止条件 | `evidence/T-07.md` 的 `loop.log`；`T-09.md`（轮次上限）、`T-10.md`（策略去重） |

## 二、三条硬性要求

| 要求 | 我们怎么满足 | 证据 |
| --- | --- | --- |
| 必须有 ≥1 个自我循环 | 执行→验证→诊断→修正→重执行，且**展示过一次真实失败后的自动修正**（不是重试） | `evidence/T-07.md`：12:27:35 `exit=1 ModuleNotFoundError` → 诊断 `switch_tool` → 12:27:36 `exit=0` → L3/L4 通过 |
| 必须体现多 Agent 协作 | 四个角色（planner / executor / verifier / writer）由调度器按分数派活，执行者可被改派 | `evidence/T-07.md` 的 `dispatch.log`：N1 planner-1、N2/N5/N6 executor-1、N7 verifier-1、N9 writer-1 |
| 必须基于 LLM 作为推理核心 | `harness/llm.py` 四个钩子（规划 / 生成脚本 / 诊断 / 报告），`--llm` 开关；无 Key 自动降级 | `python -m harness run --case T-07 --llm` 后看 `artifacts/T-07/llm.log`（每条含 model / tokens / latency） |

> **如实说明**：仓库里公开的实测指标是**接真实模型**（DeepSeek 官方端点 `deepseek-chat`）测得的：10 条用例 37 次调用、18151 tokens、交付 9/10、平均收敛 1.30 轮、P95 13.74 s。未配置 Key 时内核自动降级为确定性实现，机制完全一致但数字会变（交付 5/5/8、平均 1.40 轮、P95 0.21 s）——两组数据不混用。逐条原始日志见 `evidence/`，复现方式见 `docs/LLM实测记录.md`。

## 四、可复现性

```bash
python -m harness run --case T-07      # 单条：失败→修正→通过
python -m harness suite --mode all     # 三档基线：single / chain / full
python -m harness metrics              # 指标汇总
```

判据：接模型模式下 `full` 应为 9/10 交付（8 通过 + 1 转人工），`single`、`chain` 各 5/10；平均收敛轮次 1.30、37 次模型调用。降级（不配 Key）模式下为 8/10、1.40 轮——两者都算通过。
**换机器只允许耗时变化，通过率与轮次必须一致**——不一致就是内核行为变了。

## 五、第二套独立实现（回应"验证不能是模型自评"）

| 文件 | 作用 | 验证方式 |
| --- | --- | --- |
| `src/lib/agents/plan-verifier.ts` | 计划级规则核验（11 个 code，纯函数，不调模型） | 见下 |
| `tests/plan-verifier.test.mjs` | 27 条用例 | `node --experimental-strip-types --test --test-isolation=none tests/plan-verifier.test.mjs` → 27 pass |
| `docs/核验模块说明.md` | 规则口径、边界与局限 | 文档 |

它和 Python 内核里的 L1–L4 是**两条互不依赖的实现**：一处用 TypeScript 规则核验计划结构，一处用 Python 沙箱执行核验数值。任何一方说"通过"都不构成结论，必须两边都过。

## 六、三条一票否决，我们怎么避开的

| 否决线 | 我们的状态 |
| --- | --- |
| 纯 PPT / 无代码 | 有可运行系统：Python 内核 + Next.js 控制台，三命令出全部结论 |
| 单 Agent 封装 | 四个角色 + 调度器派活 + 改派日志，`dispatch.log` 可逐行看 |
| 直接套现成框架默认示例 | 自研 DAG 执行器、四因子调度、五级判据、三种终止条件；未使用 LangChain/Dify 等框架 |

## 七、质量保障（怎么证明它不是一次性的演示）

| 层次 | 文件 | 命令 | 现状 |
| --- | --- | --- | --- |
| 编排内核单元测试 | `tests/test_kernel.py`（19 条） | `python -m unittest discover -s tests -p "test_*.py"` | 19 passed |
| 计划核验器测试 | `tests/plan-verifier.test.mjs`（27 条） | `node --experimental-strip-types --test --test-isolation=none tests/plan-verifier.test.mjs` | 27 passed |

| 许可 | `LICENSE` | — | MIT |

单元测试覆盖的是最容易回归的四块：调度打分与"最高分者仍高负载才改派"的触发条件、三条终止条件（轮次上限 / 预算耗尽 / 策略去重）、故障注入的口径（空值注入 40 行 = 33%、量纲只污染 B 组、缺列摘 `group`）、以及验证器的相对误差定义与两条独立复算路径互相印证。

**一句实话**：这些测试证明的是"内核逻辑没坏"，不是"指标有统计学意义"。指标口径与边界见第五节，实测条件见方案书 §7.1（本仓库指标为接真模型口径：37 次调用 / 18151 tokens；不配 Key 时降级为规则实现，命令与机制不变、数字会变）。
